# `server/certs/` — development TLS material

Generated by:

```bash
python tools/make_dev_certs.py --ip 192.168.1.42
```

**Everything in here except this README is git-ignored.**

| File | What | Secret? |
| --- | --- | --- |
| `ca_key.pem` | development CA private key | **yes** |
| `ca_cert.pem` | development CA certificate | no — it is public by nature |
| `server_key.pem` | server private key | **yes** |
| `server_cert.pem` | server certificate, signed by the CA | no |

The CA certificate is also copied to `main/server_ca_cert.pem`, which the firmware
embeds at build time. The device pins that single certificate instead of trusting a
bundle of public roots — right for a private server, and about 64 KB smaller.

Keys are P-256 (ECDSA) rather than RSA: a much smaller handshake for a constrained
client, and the ESP32 accelerates the underlying big-integer arithmetic.

## The `--ip` value matters

It goes into the certificate's `subjectAltName`, and the device checks it against
the address it actually dialled. If `OTA_SERVER_URL` says `https://192.168.1.42:8443`
then the certificate must carry `192.168.1.42`. A mismatch fails the handshake —
correctly. Regenerate and re-flash if your address changes.

## These are self-signed development certificates

Fine for a private LAN demonstration where the device pins the CA. A real
deployment would use a certificate from a CA the fleet already trusts, plan for
expiry and rotation, and not keep the CA private key next to the server it signs
for.

Certificate verification is never disabled on the device — there is no insecure
option in the firmware. If TLS fails, the update does not happen.
