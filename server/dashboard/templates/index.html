    1 Build the firmware

    Runs idf.py build on this PC and writes the version numbers into main/app_config.h, so the source always matches the image. The built .bin is handed straight to step 3 — you do not need to find it on disk.

    What this changes, and what it does not
    • It edits two constants in main/app_config.h — the firmware version and the security version — and nothing else. If either is not found exactly once, the edit is abandoned rather than guessed at.
    • It runs your normal build. No extra flags; the target and configuration come from the project. The same build/secure_ota.bin you would get by hand.
    • It signs nothing. Building and signing stay separate steps, so you can look at what was built before authorising it.
    • It needs ESP-IDF on this machine. If the toolchain is not found, this step says so and you can upload a .bin in step 2 instead.

    2 Or upload a .bin you already have

    What happens to the file when you upload it
    • The name is cleaned, not trusted. Folders, drive letters, .., spaces and odd characters are stripped, so the file always lands inside server/firmware/uploads/ and nowhere else. Your original name is kept in the record.
    • Size is capped as it arrives. Anything over {{ max_upload_mb }} MB is refused while the body is still being received, and capped again as it is written. There is no lower limit beyond “not empty” — a small file is stored and reported for what it is, not turned away.
    • Nothing partial is ever kept. The upload is written to a temporary file and moved into place only when it is complete, so an interrupted upload leaves nothing you could accidentally sign.
    • SHA-256 identifies it. Re-uploading the same bytes reuses the existing copy instead of making a duplicate.
    • The image is inspected. The ESP32 header is read and reported — chip, project name, app version, IDF version. A file that is not an ESP32 image is still stored, but it is flagged.
    • No key is touched, and uploads are never downloadable. There is no route that serves a file back out of the uploads folder.

    3 Make it a secure package

    What "secure" means here

    Your plaintext .bin is hashed with Ascon-Hash256, encrypted with Ascon-AEAD128 under a fresh nonce, and the result is signed with Ed25519. The signing key stays in keys/ on this machine and never reaches your browser. The device checks all three before it writes a single byte to flash, and refuses anything older than the security version it is already running.

    4 Send it to your devices

    A new package is staged — built, but invisible to devices. Publish it when you are ready; the device picks it up on its next check. Publishing copies the signed bytes unchanged.

    How the encryption and decryption work

    Two different keys do two different jobs. A shared Ascon key hides the firmware and proves it was not altered in transit. A private Ed25519 key, which no device ever holds, proves you approved it. Every device can decrypt; only this machine can authorise.

    On this PC, when you press “Create secure package”

    1. Ascon-Hash256 over the plaintext. A 32-byte digest of your .bin exactly as you built it. This is the fingerprint the device will reproduce at the very end to prove the image it decrypted is the image you signed.
    2. Ascon-AEAD128 encryption. The firmware is encrypted under the shared key with a fresh random 16-byte nonce — never reused, so packaging the same image twice produces different ciphertext. The header’s first 80 bytes go in as associated data: they are not encrypted, but they are covered by the 16-byte authentication tag, so the version and size fields cannot be edited without breaking it.
    3. Ed25519 signature. The first 96 bytes of the header — which by now contain the digest, the nonce, the AEAD tag, the version and the security version — are signed with the private key in keys/. Because the signature covers the AEAD tag, someone who steals the shared Ascon key can read your firmware but still cannot forge a package.
    firmware_vX.sota
    signature 64 B header 96 B
    digest · nonce · tag · versions     ciphertext + tag
    Ed25519 signs bytes 0–95 · Ascon-AEAD128 authenticates bytes 0–79 as associated data

    On the ESP32, in this order — and it stops at the first failure

    1. Ed25519 verify — against a public key compiled into the device’s own image, not one taken from the package. This happens before a single byte of firmware is downloaded. Fails → INVALID SIGNATURE, nothing else runs.
    2. Anti-rollback — the package’s security version is compared against the highest the device has ever accepted, stored in NVS. A perfectly signed older package is still refused. Fails → ROLLBACK DETECTED.
    3. Ascon-AEAD128 decrypt — streamed in 4 KB chunks straight into the inactive OTA partition. The image is never held in RAM; the whole update costs about 9.3 KB regardless of firmware size. The tag is checked at the end, in constant time. Fails → ASCON AUTHENTICATION FAILED.
    4. Ascon-Hash256 compare — the digest of what was actually decrypted is compared against the digest inside the signed header. This is what ties the plaintext to your signature. Fails → the partition is abandoned.
    5. Switch the boot partition — only now, and only after all four passed. The running firmware was never touched, so a failure at any step above leaves the device exactly as it was.

    The stage names in What is happening now at the top of this page are these same steps, reported by the device as it performs them. The server does none of this work and holds no keys — it stores bytes and hands them over.

    Attack tests — prove it rejects bad firmware

    Each test builds a genuinely hostile package with tools/tamper_package.py and then asks tools/verify_package.py to accept it. You see every verification stage and exactly which one catches the attack. PROTECTED means the attack was detected and the update refused. VULNERABLE would mean a tampered package got through — it never should.

    Is any of this sent to my device?

    No. A hostile package is built in a temporary folder, refused by the verifier, and the folder is deleted. It is never written to server/packages/, never published and never offered over the OTA API. What these tests prove is a property of the package format, checked on this PC. The ESP32 runs the same checks in C — the same sources the host test suite compiles and runs — and docs/DEMO.md shows the device itself rejecting a package.

    How to use

    First time only

    1. Install the Python dependencies. In the ESP-IDF PowerShell, from the project folder: 
      pip install -r server/requirements.txt
    2. Create the keys. This writes the Ed25519 pair and the Ascon key into keys/, and the device's copy of the public key into main/crypto_config.h: 
      python tools/generate_keys.py --write-device-config
      Without this, step 2 on this page cannot sign anything and will say so.
    3. Tell the firmware where to find this server. Copy main/device_config.h.example to main/device_config.h and fill in your Wi-Fi name, Wi-Fi password and this PC's LAN IP address.
    4. Build and flash the first firmware so the board has something to update from: 
      idf.py set-target esp32
idf.py build flash monitor
    5. Start this server in a second ESP-IDF PowerShell window: 
      python server/app.py
      Then open http://localhost:8000/.

    Every time you want to update a device

    1. Build the new firmware. Raise the version in main/app_config.h first — both the version and, if this update fixes something security-related, SECURITY_VERSION. Then: 
      idf.py build
      Do not flash it over USB. The new image is build/secure_ota.bin.
    2. Upload it in step 1 above. Drag build/secure_ota.bin onto the box, or pick it with the file chooser. The page will tell you what it found inside the image — check that the app version is the one you just built.
    3. Create the package in step 2. Choose the file you just uploaded, type the same version you set in app_config.h, set the security version, and press the button. Every stage is listed as it completes, ending in a self-check that the package verifies.
    4. Publish it in step 3. Until you do, the device is offered nothing. After you do, the device downloads it on its next check (within about a minute), verifies it, installs it and reboots.
    5. Watch the board. In the window running idf.py monitor you will see the signature, version, decryption and hash checks pass, the install, and the reboot into the new version.

    If something goes wrong

    "missing ed25519_private.pem" in step 2
    The keys have not been generated. Run python tools/generate_keys.py --write-device-config, then rebuild and re-flash the firmware so the board has the matching public key.
    The upload is flagged "not an ESP32 application image"
    The file does not begin with 0xE9. You have almost certainly picked the wrong .bin — use build/secure_ota.bin, not the bootloader or the partition table. The file is kept, but a device would refuse to boot it.
    "already exists — packages are never overwritten"
    That version has been built before. Bump the version number; a signed package is never rewritten in place, because that is exactly what an attacker would want to do.
    The device never picks up the update
    Check that the package is published and not just staged, that OTA_SERVER_URL in main/device_config.h points at this PC's LAN IP (not localhost), and that the board and the PC are on the same network.
    The device rejects the update
    That is the system working. The serial console names the check that failed: a bad signature, a rollback to an older security version, a failed decryption or a hash mismatch. Nothing was written to flash and the old firmware keeps running.

    This server holds no cryptographic keys of its own — it stores and serves bytes. Signing happens in tools/create_ota_package.py on this machine, and every check that matters is repeated on the device. Plain HTTP is for development only.
